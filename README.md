# gh-actions-templates

Reusable GitHub Actions workflows shared across m13tLabs repos, called via `uses:`.

## ansible-role-ci.yml

CI for an Ansible role: `ansible-lint` and `molecule test` across a matrix of `ansible-core`
versions, plus an end-to-end install job (no container) on Linux and macOS. `molecule` and
`end2end` auto-detect whether the calling repo has `molecule/default/molecule.yml` /
`tests/e2e/playbook.yml` and no-op their steps when absent, so the workflow is safe to use
even before those scenarios exist.

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [develop]
  pull_request:

jobs:
  ci:
    uses: m13tLabs/gh-actions-templates/.github/workflows/ansible-role-ci.yml@main
```

### Inputs

| Input | Default | Description |
| --- | --- | --- |
| `ansible_versions` | `["2.14",...,"2.21"]` | JSON array of `ansible-core` minors to test |
| `lint_os` | `["ubuntu-latest","macos-latest"]` | JSON array of runner OSes for `ansible-lint` |
| `e2e_os` | `["ubuntu-latest","macos-latest"]` | JSON array of runner OSes for the end-to-end job |
| `e2e_python_version` | `"3.14"` | Python version used to install `ansible-core` for the end-to-end job |

## ansible-role-release.yml

Manual release: bumps `config.json`, regenerates `README`/`meta/argument_specs.yml`,
updates `CHANGELOG.md` via `git-cliff`, tags, and creates a GitHub Release — authenticated
as a GitHub App rather than the default token so the release commit can push to a
protected default branch.

```yaml
# .github/workflows/release.yml
name: Release

on:
  workflow_dispatch:
    inputs:
      release_type:
        type: choice
        required: true
        default: patch
        options: [patch, minor, major, custom]
      custom_version:
        type: string
        required: false

jobs:
  release:
    uses: m13tLabs/gh-actions-templates/.github/workflows/ansible-role-release.yml@main
    with:
      release_type: ${{ inputs.release_type }}
      custom_version: ${{ inputs.custom_version }}
      app_id: ${{ vars.CI_APP_ID }}
      # only needed if this repo's README isn't lowercase "README.md"
      readme_filename: "README.MD"
    secrets: inherit
```

### Inputs

| Input | Default | Description |
| --- | --- | --- |
| `release_type` | — (required) | `patch`, `minor`, `major`, or `custom` |
| `custom_version` | `""` | Explicit version, required when `release_type: custom` |
| `app_id` | — (required) | GitHub App ID; pass `${{ vars.CI_APP_ID }}` from the calling repo |
| `default_branch` | `"develop"` | Branch released from and pushed back to |
| `readme_filename` | `"README.md"` | README filename regenerated by `ansible-docsmith` (case-sensitive) |
| `draft_release` | `true` | Create the GitHub Release as a draft |

### Secrets

`secrets: inherit` forwards `CI_PRIVATE_KEY` (the GitHub App's private key) automatically —
it must be defined under that exact name in the calling repo or its org. `app_id` is a
`vars.*` value, not a secret, so it's passed explicitly via `with:` rather than inherited.

## Versioning

Callers pin a ref after `@` — `@main` tracks the latest, or pin a tag (e.g. `@v1`) for
stability and bump it deliberately. There is no compatibility guarantee across changes to
`main`.
